# 内核升级：`dsh 0.2.0-rc.2` → `0.2.1-rc.2`

> 日期：2026-10-19 ｜ 结论：**升级成功，五个插件在 0.2.1-rc.2 上全部正常**
> 本文记录「查了什么、怎么验的、变了什么、没采纳什么」，供下次换代照做。

---

## 1. 为什么要升

- 上游 `@deepseek-ai/dsh` 的 `next` 通道已经在 `0.2.1-rc.2`（`npm dist-tags`：`latest=0.2.0-rc.2`、`next=0.2.1-rc.2`）。
- **用户实际在跑的桌面端就是 0.2.1-rc.2**（`resources/app.asar` 内 package.json）。
- 本仓库的随包内核原先停在 0.2.0-rc.2 ⇒ 独立壳里的内核比桌面端落后一个版本。

---

## 2. 0.2.0 → 0.2.1 到底变了什么

### 2.1 包级差异（`@deepseek-ai` scope 目录对比）

| | 0.2.0-rc.2 | 0.2.1-rc.2 |
| --- | --- | --- |
| scope 内包数 | 287 | 306 |
| 新增 | — | `dsh-plugin-market`、`dsh-experimental-inspector*`、`dsh-tool-schedule`、`dsh-tool-terminal`、`dsh-working-directory`、`dsh-experimental-session-search`、`dsh-web-deepseek-api` 等 25 个 |
| 移除 | — | `dsh-client-store`、`dsh-client-ui-slots`、`dsh-client-ui-primitives`、`dsh-hook-protocol`、`dsh-hooks-claude-code`、`dsh-hooks-codex`、`dsh-invariants`、`dsh-webhook`、`dsh-webhook-github`、`dsh-subagent-in-process-driver`、`dsh-experimental-schedule-bundle` |

> ⚠️ `dsh-client-ui-slots` / `dsh-client-ui-primitives` / `dsh-client-runtime` 这三个名字**在我们的插件 `dsh.client.inject` 里被声明着**，但它们在 **0.2.0 时就已经不是 boot 图里的 entry**（实测两版 boot manifest 的“找不到的 inject”集合**完全相同**：都是这 3 个）。
> ⇒ **这是既有状态，不是 0.2.1 引入的回归**；内核按“可选等待”处理，页面照常渲染。

### 2.2 关键文件逐字比对

| 包 | 0.2.0 vs 0.2.1 | 结论 |
| --- | --- | --- |
| `dsh-app-boot` / `dsh-base` / `dsh-web-app` / `dsh-plugin-manager` / `dsh` | 逐字相同 | 组装逻辑与 CLI 入口没变 |
| `dsh-settings` | 同为 22630 字节，`update/describe/replace` 三个 API 一致，**两版都没有 `settingsScope`** | 我们依赖的 settings 面没有进一步变化 |
| `dsh-client-modules` | 仅 `scripts` 字段不同（发布时是否带 build 脚本） | 功能相同 |

**兼容闸门的实现**（`dsh-app-boot`）：`semver.satisfies(runtimeVersion, range, { includePrerelease: true })`，
比较的是 **DSH 运行时版本**与插件 `peerDependencies` 里 `@deepseek-ai/dsh*` 的声明。
带 `includePrerelease` 时 `0.2.1-rc.2` 命中 `^0.2.0-rc.1`；我们仍**显式补上 `^0.2.1-rc.1`**，让意图写在字面上。

### 2.3 换代会踩的坑（来自社区同类项目的公开记录，我们据此自查）

1. **0.2.1 新增的正文宽度调节线会伸到固定 dock 下方** —— 需要给 `[data-width-handle]` 留出底部偏移。
2. **思考中再次输入会让 composer 重挂载**，输入框/工具栏/模型控件可能瞬时错位。
3. **插图（附件）后 `contenteditable` 的文字/选区可能不可见**，附件背景层压住工具栏。
4. **跨构建的旧状态不得覆盖新宿主**：升级后若旧适配状态校验失败，先重装官方原版，不要手工覆盖 asar。

> 以上 1–3 我们**尚未逐条回归**（见 §6）。

## 3. 怎么验的（三份内核树交叉验证）

| # | 内核来源 | 文件数 / 体积 | 与 Fairy profile 的实测结果 |
| --- | --- | --- | --- |
| A | `npm i @deepseek-ai/dsh@0.2.1-rc.2` 完整依赖树 | 63641 / 694 MB | ✅ 五插件 apply 全 success，页面 139 个 Fairy 节点，0 报错 |
| B | **桌面端 `app.asar` 里的官方内核**（`@electron/asar extract`） | **17262 / 405.6 MB** | ✅ 同样全绿 ⇒ **选它做随包内核（更小）** |
| C | `~/.local/node_modules`（0.2.0-rc.2 基线） | 26597 / 452.9 MB | ✅ 对照组，行为一致 |

**验收方法**（可复现）：隔离 home（`profiles/web` 用 junction 指向仓库 profile）→ 用目标内核起 `--port <n> --no-open`
→ 走 `?token=` 换 cookie → 读 `window.__DSH_BOOT__` 校验 client 模块图 → 用 Playwright(Edge) 读 DOM：

```
data-dsh-fairy-setup / visual / theme / mode / power-mode / startup-reset   六属性齐全
Fairy 相关节点 139 个，console 0 error
```

> ⚠️ **踩过的坑**：`<home>/profiles/web` 必须是 **junction**（内核只认这个路径）。
> 建成了普通空目录的话，内核会自举成裸 profile —— 表现为“插件全没加载”，但其实内核完全正常。
> 我第一次就是这么误判「官方内核跑不起来」的。

## 5. 参考了谁、没采纳什么

### 5.1 上游未合并 PR #6（`Chengzhibense/Fairy-DSH`，作者 `PhiLia011`，分支 `port/dsh-0.2.1`）

它把 0.1.1 → 0.2.1-alpha.5 的适配写完了（44 文件 / +1495 −554），四类改动：

- **Settings**：`settingsNamespace` / `ctx.settingsScope` 已移除 ⇒ 导出 **volatile `Config`**，client 用 `ctx.remote.settings.describe()/mutate()` 读写，落盘到 profile 的 `cordis.patch.yml`。
- **Startup**：`sessions.list.current` / `clear()` 已移除 ⇒ `uiWorkspace.clearMain()` + `startSession()`。**我们已采用等价实现**。
- **DOM**：不再有 `[data-slot="conversation"]`，改为 `[data-phase]` 根 + Lexical `[data-composer-input="true"]`。
- **依赖**：移除 `dsh-message-edit@0.2.3` / `dsh-reasoning-effort@0.6.2`（它们仍引用 0.1 的 client-runtime 模块表）。

**我们的判断**：PR #6 针对的是 `0.2.1-alpha.5`；到 `rc.2` 时 `[data-slot="main.conversation"]` **仍然存在**（实测我们的会话选择器 `[data-slot="conversation"], [data-slot="main.conversation"]` 命中），所以**它的 DOM 改名不能照抄**。settings 那部分（volatile Config）是对的，但我们当前**不需要**它（见 §6.1）。

### 5.2 同生态的 `FLKSSSSS/dsh-fairy-ui`（v1.4.6）

- **性质**：独立开发/再整合发行（`fork:false`），不是任何 Fairy 仓的分支；形态是「改官方桌面端 asar 主入口的插件包」。
- **许可**：⚠️ **仓库内没有 LICENSE，`package.json` 也没有 `license` 字段** ⇒ 默认保留所有权利，**不能复制它的代码/文案/素材**。
- 它把换代差异收敛成一张选择器表、并把原生控件改走官方席位（`ctx.slots.inject("conversation.input.model")` + `modelDirectories`）—— 这些**做法**值得参考，但我们**只参考思路、独立实现**，未复制任何文件。

## 6. 已知缺口与下一步

1. **设置仍走 localStorage 兜底**（不是故障）：0.2.x 已无 `settings.register`，插件因此降级为「渲染进程 localStorage」。**实测功能正常**（点 HDD 开关即时生效并写入 `dsh.fairy.localSettings.v1.*`）。
   代价：设置**不写进 profile 配置**，换 profile/重装后不跟随。
   修法即 PR #6 的路（volatile `Config` + `remote.settings`），属**独立任务**，改动会触及产物 `lib/client.js`，需按红线（产物为准 + src 同步 + 契约测试）单独排期。
2. **§2.3 的 1–3 号坑未逐条回归**：正文宽度调节线、composer 重挂载、附件后 `contenteditable` 可见性。
3. **`fairy-system` 的 capability matrix / accepted baseline 仍停在 0.1.x 时代**，未按 0.2.1 重测（与 PR #6 的“Not re-baselined”是同一件事）。
4. `dsh-experimental-schedule-bundle` 在 0.2.1 已被移除，但仓库 profile 的 `dsh.profile.bundles` 里仍列着它 —— 内核会静默跳过；下次整理 profile 时清掉。
5. 随包内核体积：0.2.1 官方内核 405.6 MB（0.2.0 为 452.9 MB）——**没有变大**。
